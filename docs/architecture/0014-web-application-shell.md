# 0014: the web application shell

- Status: accepted
- Date: 2026-09-17
- Amends: 0012's statement that the web ships a service worker that precaches
  the application shell; 0013's "The sync pass" (single-flight) and "Web"
  sections.

## Context

An audit of the web build against 0012 and 0013 found that several browser
behaviors had been worked around where they needed designing for. Each was
verified in a browser or in the source of the library involved:

- The offline service worker was hand-written runtime caching. It began caching
  only once it controlled the page, after Flutter had fetched its entry files,
  so an app visited once did not open offline. With Workers Static Assets'
  default `Cache-Control: public, max-age=0, must-revalidate`, a headless Chrome
  cold start with the origin down showed the browser's error page after one
  visit. It also served unhashed entry points cache-first, so the
  update-required reload came back to the old build, and could mix files from
  two builds.
- Drift's web runtime (`sqlite3.wasm`, `drift_worker.js`) was copied into every
  app and into the scaffold, pinned by a README note while `drift` floated on a
  caret.
- The browser tab lock was taken when `SharedWorker` was missing, but drift also
  falls back to per-tab IndexedDB when a shared worker exists and fails, so the
  unsafe case could open unlocked. A refused tab never recovered on its own.
- Drift's IndexedDB storage keeps a write in memory until a later statement
  runs outside a transaction, and `Sqlite3Delegate.setSchemaVersion` writes the
  schema version last, without flushing (drift 2.35.0). A browser that opened
  the replica and closed before writing anything else lost the version, and
  every later open failed creating tables that exist. Reproduced in Chrome with
  shared-worker storage.
- The sync pass lock was taken before joining a pass in flight, so a trigger
  arriving mid-pass queued a second full pass rather than joining; on native the
  lock was immediate and joining worked.
- Flutter's web engine maps window `blur` and `focus` to `inactive` and
  `resumed`, so `onResume` fired on every alt-tab and when the sign-in popup
  closed, each time running a sync pass and reconnecting an open game's socket.
- `connectivity_plus` on the web reports only `online` and `offline` events and
  never the state it starts in, so an app opened offline believed itself online
  and did not sync when the network returned.
- Closing the Google sign-in popup, or a blocked popup, showed a generic error.

## Decision

### The service worker is generated by Workbox and precaches the build

The web build ends with `workbox generateSW workbox-config.cjs`. The worker
precaches everything the app is built from when it installs: `index.html`,
`flutter_bootstrap.js`, `main.dart.*`, the manifest, icons, and `assets/`. A
navigation is answered with the precached `index.html`, except for the routes
the game Worker renders itself, which the configuration's
`navigateFallbackDenylist` names: `run_worker_first` less `/join/*` and
`/game/*`. The scaffold's tests hold the two lists together.

CanvasKit and the Firebase JS SDK load from Google's CDN at URLs that name their
version, so the worker caches them cache-first as they load. A first visit loads
them before the worker controls the page, so `flutter_bootstrap.js` copies what
the page loaded into the same cache, and drops versions it no longer loads.

`flutter_bootstrap.js` starts Flutter at once and registers the workers beside
it rather than awaiting them first.

### A deploy waits, and the update-required action activates it

The worker does not skip waiting. A new deployment's worker precaches the new
build beside the old one and takes over when no tab runs the old build, so a
running tab never mixes two builds. When the engine refuses a client as too old,
the web's update-required action asks the browser for the newest worker, waits
for it to install, sends it Workbox's `SKIP_WAITING` message, and reloads once
it controls the page.

### Drift's web runtime ships with `eigen_flutter`

`sqlite3.wasm` and `drift_worker.js` are web-only package assets of
`eigen_flutter`, served at `assets/packages/eigen_flutter/assets/drift/`.
`eigen_flutter` holds `drift` to the minor line the files come from
(`>=2.35.0 <2.36.0`), because the worker and the module are one pair from one
drift release. An exact pin would be tighter, but pub does not publish a
single-version constraint, and drift keeps its worker protocol compatible within
a minor line. No app or template carries a copy.

### Storage is chosen, then locked, then opened

The web replica host probes the browser, chooses the most reliable storage
(keeping an existing database in the storage it is in), and only then decides
whether this tab may open it:

- Storage a shared worker hosts for every tab (`opfsShared`, `sharedIndexedDb`)
  opens in every tab.
- Per-tab IndexedDB (`unsafeIndexedDb`) opens only in the tab holding the
  database's Web Lock for its lifetime. Another tab reports that the app is
  open elsewhere, waits for the lock, and opens by itself when it is granted.
- Memory opens, and the app says nothing survives a reload.

A host is created already knowing its storage. On IndexedDB storage, one
statement runs straight after the database first opens, so the schema version
opening wrote is persisted.

### A sync request is answered by a pass that began after it

This replaces single-flight joining. Passes over one replica never overlap: the
pass takes a lock that, on the web, is the Web Lock every tab shares. A request
records when it was made, and once it holds the lock it runs a pass only if the
account's `last_synced_at` is older than that moment. `last_synced_at` is the
moment the last completed pass sent its first pull request, written only by the
page that completes the pass. A burst of requests, from one process or from
several tabs over one database, therefore costs one pass; a request made while a
pull is already under way still gets a pass of its own, because that pull may
have been answered before whatever prompted the request; and a failed pass
answers no request.

### Coming back is `onShow`

The app refreshes (sync pass, update check, notification reconciliation, the
open game's streams) when it comes back into view, `AppLifecycleListener.onShow`,
not when it regains focus. On Android this also stops the notification shade
from triggering a pass.

### Connectivity starts from the current state

The connectivity provider reads the current state explicitly, then follows
changes; a change that arrives before the read answers wins.

### Web sign-in is the popup, and its outcomes are modelled

The web signs in and upgrades a guest through Firebase's popup, with no redirect
fallback. `AuthGateway` reports a dismissed sign-in as `cancelled`, which is not
an error and leaves a guest untouched, including during a switch to an existing
account. A popup the browser blocks is `AuthWindowBlockedException`, which the
app explains. The Firebase adapter maps `popup-closed-by-user`,
`cancelled-popup-request`, and `user-cancelled`, and Google Sign-In's `canceled`,
to `cancelled`, and `popup-blocked` to blocked.

## Invariants

Unchanged from 0013. New:

- A web tab runs one build, from one precache, until it reloads.
- A browser tab opens per-tab storage only while holding its lock.
- A sync request is answered by a completed pass that began pulling after it.

## Testing

- `eigen_client`: requests made before a pass begins pulling share it; a request
  made mid-pull runs again; a failed pass answers nothing; passes sharing a lock
  answer each other; `last_synced_at` changes only on a pass's last page.
- `eigen_flutter`: an app opened with no network is offline before any change,
  and a change arriving before the read wins.
- `eigen_firebase`: interruption codes map to cancelled or blocked, and nothing
  else does.
- `eigen_shell`: a dismissed sign-in is not an error, and a dismissed switch
  keeps the guest.
- `tool/check.sh flutter` builds the example, generates its worker, and checks
  the worker precaches the entry points and drift's runtime. The scaffold's
  end-to-end check runs the project's own `build:web`, and its tests hold the
  worker's denylist to the Worker's routes.

Browser behavior is not covered by CI and was verified in headless Chrome when
this was decided: an offline cold start after one visit with every host but the
origin unreachable, an offline `/game/:id` link, the update handshake, two tabs
over shared-worker storage, a refused tab taking over, and reopening after the
only tab closed.

## Open questions

- Chrome for Android shipped shared workers in Chrome 148, with a documented
  caveat that one may be terminated when the app is backgrounded. What drift's
  connection does then is untested on a device.
- The schema-version flush works around drift; it should be reported upstream
  and removed once drift persists `setSchemaVersion` itself.
- `navigator.storage.persist()` prompts in Firefox, and is asked when the first
  local game is created rather than behind an explanation.
